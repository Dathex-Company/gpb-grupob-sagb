## 🔴 Problemas encontrados (3 críticos — CORRIGIDOS)

### P1 — RPCs SECURITY DEFINER sem validação de perfil (🔴→🟢)

**Gravidade:** 🔴 Crítica  
**Descrição:** As 3 RPCs eram `SECURITY DEFINER` mas não verificavam se o usuário chamador tinha perfil adequado. Como `SECURITY DEFINER` bypassa RLS, um usuário `leitor` poderia publicar documento ou restaurar versão.

**Correção aplicada:** Adicionada validação `auth.jwt() -> 'app_metadata' ->> 'profile_role'` no início de cada RPC:

| RPC | Perfis permitidos |
|---|---|
| `cp_save_document_draft` | `editor`, `curador`, `aprovador`, `administrador` |
| `cp_publish_document` | `aprovador`, `administrador` |
| `cp_restore_document_version` | `administrador` |

---

## 🟡 Observações (não bloqueantes)

### O1 — SELECT policies abertas para authenticated

Todas as policies `_select` usam `using (true)`. Isso significa que qualquer usuário autenticado pode ver versões, rascunhos e eventos de qualquer documento. É consistente com a política de transparência da Central, mas deve ser revisado se houver documentos com informações sensíveis.

### O2 — Editor pode ver rascunhos de outros editores

A policy `cp_doc_drafts_select` permite que qualquer `editor` veja rascunhos de qualquer documento. Isso é intencional para colaboração, mas pode ser restringido no futuro.

### O3 — Sem soft-delete nas novas tabelas

As tabelas `versions`, `drafts` e `events` não têm coluna `deleted_at`. Isso é aceitável pois:
- `versions` são histórico imutável
- `drafts` são efêmeros e têm política de delete
- `events` são log de auditoria
