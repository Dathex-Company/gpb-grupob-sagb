# Plano 01.13 — R5 Document Hub V1 — Supabase Schema, Storage, RPC e Persistência

Data: 2026-06-13  
Módulo: `src/modules/central_padroes`  
Origem: itens R5 identificados no plano consolidado `01.12-plano-execucao-consolidado-document-hub-v1.md`.  
Restrição: este documento é apenas plano. Nenhuma migration, policy, RPC, storage ou código-fonte foi alterado nesta etapa.

---

## 1. Objetivo

Isolar tudo que exige alteração de Supabase remoto, schema, storage, RLS/policies, RPC ou pipeline semântico para que o Document Hub V1 possa evoluir sem misturar tarefas seguras de frontend/read-only com operações R5.

---

## 2. Itens R5 identificados

| Área | Item | Motivo R5 |
|---|---|---|
| Schema | Expandir `central_padroes_documents` | Persistência rica de documentos vivos. |
| Schema | Criar índices para campos novos | Performance de filtros e busca. |
| RLS/policies | Ajustar permissões documentais | Ações por perfil precisam ser coerentes no banco. |
| Service/RLS | Soft delete obrigatório | Evitar DELETE real e preservar histórico. |
| Storage | Padronizar buckets oficiais | Há divergência entre service, module-doc e migrations. |
| RPC | Revisar `central_padroes_ingest_document` | Contrato atual precisa atender Hub, triagem, storage e auditoria. |
| Storage/RPC | Upload real de documento/evidência | Hoje o service não faz upload em bucket. |
| Search | Ativar `central_padroes_search_index`/pgvector no fluxo | Schema existe, mas frontend ainda usa busca textual. |
| Editor | Salvar conteúdo markdown | Requer `content` ou storage path persistente. |

## 3. Diagnóstico R5 atual

### 3.1 Tabela `central_padroes_documents`

Estado atual identificado nas migrations:

- criada com campos mínimos: `id`, `title`, `source_path`, `status`, `category`, `area_id`, `destination_type`, `created_at`, `updated_at`;
- migration V3 adicionou `deleted_at` e `deleted_by`;
- RLS atual permite SELECT com `deleted_at is null`, INSERT por perfis editor+ e UPDATE por curador/aprovador/admin;
- policy chamada `cp_documents_delete` é, na prática, policy de UPDATE para soft delete;
- frontend ainda executa DELETE real em `centralPadroesCrudService.deleteDocument()`.

Campos necessários para Document Hub persistente:

- `slug`;
- `type`;
- `risk_level`;
- `owner`;
- `tags`;
- `summary`;
- `content`;
- `path_absolute`;
- `path_relative`;
- `source`;
- `module`;
- `division`;
- `canonical_level`;
- `created_by`;
- `updated_by`.

### 3.2 Storage

Divergências encontradas:

| Fonte | Buckets citados |
|---|---|
| `module-doc.ts` | `canonical-documents`, `evidence-files` |
| `centralPadroesStorageService.ts` | `central-padroes-documents`, `central-padroes-evidence`, `central-padroes-templates` |
| migration V5 | `cp-documents`, `cp-evidence` |

Decisão recomendada: padronizar em `cp-documents` e `cp-evidence`, pois já existem na migration V5 e possuem policies em `storage.objects`.

### 3.3 RPC de ingestão

RPC encontrada: `central_padroes_ingest_document`.

Contrato atual no frontend:

- endpoint REST: `rpc/central_padroes_ingest_document`;
- parâmetros enviados: `p_title`, `p_source_path`, `p_raw_content`, `p_source_kind`;
- retorno tratado como string.

Lacunas:

- retorno deveria ser estruturado com `queue_id`, `document_id`, `status`, `warnings`;
- não há integração clara com storage path;
- não registra auditoria detalhada da ingestão;
- não valida bucket;
- não classifica origem no vocabulário do Hub;
- não preenche campos ricos da futura tabela `central_padroes_documents`.

### 3.4 Search index e pgvector

`central_padroes_search_index` existe com `embedding` e `search_vector`, mas o frontend mantém busca textual ampliada.

R5/fase futura necessária para:

- definir pipeline de reindexação;
- criar ou revisar RPCs de upsert/rebuild;
- gerar embeddings;
- controlar permissões por `allowed_roles`;
- sincronizar DocumentHubService, SearchService, IndexService e Chat Pietro.

## 4. Migration proposta para schema documental

Nome sugerido:

`supabase/migrations/20260613000101_central_padroes_document_hub_v1_documents.sql`

Conteúdo conceitual:

```sql
alter table public.central_padroes_documents
  add column if not exists slug text,
  add column if not exists type text not null default 'documento',
  add column if not exists risk_level text not null default 'baixo',
  add column if not exists owner text,
  add column if not exists tags text[] not null default '{}',
  add column if not exists summary text,
  add column if not exists content text,
  add column if not exists path_absolute text,
  add column if not exists path_relative text,
  add column if not exists source text not null default 'manual',
  add column if not exists module text,
  add column if not exists division text,
  add column if not exists canonical_level text,
  add column if not exists created_by uuid references auth.users(id),
  add column if not exists updated_by uuid references auth.users(id);

create index if not exists idx_cp_documents_slug on public.central_padroes_documents(slug);
create index if not exists idx_cp_documents_type on public.central_padroes_documents(type);
create index if not exists idx_cp_documents_risk on public.central_padroes_documents(risk_level);
create index if not exists idx_cp_documents_owner on public.central_padroes_documents(owner);
create index if not exists idx_cp_documents_source on public.central_padroes_documents(source);
create index if not exists idx_cp_documents_canonical_level on public.central_padroes_documents(canonical_level);
create index if not exists idx_cp_documents_tags on public.central_padroes_documents using gin(tags);
```

Observações:

- avaliar `check` constraints para `risk_level`, `source`, `type` e `canonical_level` somente depois de confirmar vocabulário final;
- se houver dados legados com status divergentes, usar normalização no frontend antes de constraints fortes;
- `slug` pode ser unique posteriormente, mas inicialmente pode haver colisões entre `.md`, Supabase e governance.

## 5. RLS/policies propostas

### 5.1 Ações documentais esperadas

- visualizar documento;
- criar documento;
- editar metadados documentais;
- editar conteúdo documental;
- enviar para curadoria;
- publicar/canonizar documento;
- arquivar documento;
- restaurar documento;
- anexar evidência;
- reindexar documento.

### 5.2 Regras recomendadas

| Perfil | Regras de documento |
|---|---|
| leitor | SELECT de documentos não deletados e permitidos. |
| editor | INSERT e edição de rascunhos próprios, sem publicar. |
| curador | edição de metadados, triagem, curadoria, arquivamento não crítico. |
| aprovador | aprovar/canonizar/publicar conforme gates. |
| administrador | todas as ações, incluindo restore e ajustes de schema operacional. |
| auditor | SELECT e logs, sem alteração. |
| agente_autorizado | leitura conforme allowed_roles e registro de consulta, sem edição. |

### 5.3 Funções auxiliares recomendadas

- `cp_can_edit_document(document_id uuid)`;
- `cp_can_edit_document_content(document_id uuid)`;
- `cp_can_publish_document(document_id uuid)`;
- `cp_can_archive_document(document_id uuid)`;
- `cp_can_restore_document(document_id uuid)`.

## 6. Storage e buckets

### 6.1 Decisão de nomes

Padronizar:

- `cp-documents` para documentos, markdown, PDF, DOCX e texto;
- `cp-evidence` para evidências, prints, PDFs e anexos de validação.

### 6.2 Ajustes necessários

- atualizar `module-doc.ts` para refletir buckets reais;
- atualizar `centralPadroesStorageService.ts` para usar `cp-documents` e `cp-evidence`;
- remover ou justificar `central-padroes-templates`, ou criar bucket correspondente em migration própria;
- definir path convention:
  - `documents/{document_id}/{slug}.md`;
  - `documents/{document_id}/attachments/{filename}`;
  - `evidence/{entity_type}/{entity_id}/{timestamp}-{filename}`.

### 6.3 Policies de storage

Validar se policies existentes cobrem:

- select autenticado;
- insert por editor+;
- update por curador+;
- remoção lógica ou restrição de delete;
- separação de evidência crítica.

## 7. RPC de ingestão revisada

Nome recomendado:

- manter `central_padroes_ingest_document` com contrato expandido; ou
- criar `cp_document_hub_ingest_document` e manter a antiga como compatibilidade.

Parâmetros sugeridos:

```sql
p_title text,
p_source_path text default null,
p_raw_content text default null,
p_source_kind text default 'manual',
p_storage_bucket text default null,
p_storage_path text default null,
p_owner text default null,
p_tags text[] default '{}',
p_risk_level text default 'baixo',
p_module text default null,
p_division text default null,
p_create_document boolean default false
```

Retorno sugerido:

```json
{
  "queue_id": "uuid",
  "document_id": "uuid|null",
  "status": "queued|created|triage|blocked",
  "warnings": [],
  "source": "manual|md_indexado|upload|external"
}
```

Comportamento esperado:

- registrar item na fila de ingestão;
- opcionalmente criar documento em `central_padroes_documents` quando autorizado;
- preencher metadados ricos quando disponíveis;
- registrar audit log;
- retornar estrutura previsível;
- nunca prometer salvar arquivo local em `Z:\`.

## 8. Editor persistente e conteúdo markdown

Dependências antes de implementar `DocumentoEditorPage` com salvamento real:

- schema documental expandido aplicado;
- RLS/policies revisadas;
- decisão entre `content` em tabela e/ou arquivo em storage;
- service frontend usando campos novos;
- audit log em salvar conteúdo;
- reindex após salvar;
- fallback de erro claro.

Regras:

- sem R5 aplicado, editor pode existir apenas em modo preview/readonly ou metadados básicos;
- botão “Salvar conteúdo” deve ficar oculto/desabilitado se persistência real não estiver confirmada;
- qualquer salvamento de conteúdo deve registrar `UPDATE` ou `CANONICAL_EDIT` conforme canonicidade.

## 9. Search index e pgvector

Fase R5 opcional/posterior ao Hub V1 funcional:

- definir fonte de embeddings;
- criar job/RPC de rebuild;
- popular `central_padroes_search_index` a partir do DocumentHubService ou equivalente server-side;
- sincronizar `allowed_roles`;
- integrar SearchService e Chat Pietro ao index remoto com fallback textual;
- manter auditoria de reindexação.

RPCs possíveis:

- `cp_rebuild_document_hub_search_index()`;
- `cp_upsert_document_hub_search_entry(entity_type, entity_id)`;
- `cp_search_document_hub(query, filters jsonb)`.

## 10. Ordem R5 recomendada

1. Confirmar vocabulário final de `type`, `status`, `risk_level`, `source` e `canonical_level`.
2. Aplicar migration de campos ricos em `central_padroes_documents`.
3. Aplicar índices.
4. Revisar RLS/policies documentais.
5. Padronizar buckets para `cp-documents` e `cp-evidence`.
6. Atualizar ou criar RPC de ingestão com retorno estruturado.
7. Atualizar service frontend para buckets/RPC/schema novos.
8. Trocar delete real por soft delete no frontend.
9. Implementar salvamento real de conteúdo markdown.
10. Integrar audit log e reindex.
11. Validar com testes e QA autenticado.
12. Só então liberar `DocumentoEditorPage` persistente.

## 11. Critérios de pronto R5

- [ ] `central_padroes_documents` possui campos ricos e índices aplicados.
- [ ] RLS/policies impedem ações indevidas por perfil.
- [ ] Buckets oficiais estão padronizados em schema, service e documentação.
- [ ] RPC de ingestão retorna estrutura previsível e registra auditoria.
- [ ] Upload real de documentos/evidências funciona ou está explicitamente bloqueado.
- [ ] Soft delete substitui DELETE real.
- [ ] Editor salva conteúdo markdown de forma persistente.
- [ ] Salvamento registra audit log.
- [ ] Busca/reindex refletem conteúdo salvo.
- [ ] Rollback/mitigação está documentado antes de aplicar em remoto.

---

## 12. Riscos específicos R5

| Risco | Impacto | Mitigação |
|---|---|---|
| Migration em remoto sem backup | Perda/instabilidade de dados. | Snapshot/backup e execução controlada. |
| Constraints fortes antes de normalizar dados | Falhas em registros legados. | Adicionar constraints após saneamento. |
| Buckets divergentes persistirem | Upload falha em produção. | Padronizar todos os contratos em uma etapa. |
| RPC antiga quebrar UI existente | Regressão em `DocumentsPage`. | Manter compatibilidade ou versionar RPC nova. |
| RLS bloquear editor legítimo | Usuários não conseguem operar. | Testes por perfil antes de liberar. |
| RLS permissiva demais | Alteração indevida de documentos. | Policies por ação e audit log obrigatório. |
| Conteúdo em tabela crescer demais | Performance ruim. | Avaliar storage para arquivos grandes e `content` para markdown textual curto. |
| pgvector virar promessa não entregue | Confusão de produto. | Manter busca textual como modo declarado até pipeline pronto. |

---

## 13. Conclusão

O R5 do Document Hub deve ser tratado como trilha própria. A V1 sem R5 pode entregar navegação, detalhe, busca, Chat Pietro consistente, triagem, auditoria, permissões e lacunas visíveis. O R5 deve entrar apenas quando houver autorização para alterar Supabase, padronizar storage/RPC e persistir conteúdo de forma confiável.
